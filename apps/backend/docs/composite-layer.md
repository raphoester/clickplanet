# The composite layer

Each context wires **itself**, in a `module.go` at its root (`internal/planet/module.go`, `internal/chat/module.go`, `internal/auth/module.go`, `internal/player/module.go`). That file is the context's manifest: its `Config`, whether it is on, and its DI sequence. **A module takes its config and nothing else, and builds every object it needs itself** — there is no `Deps` struct and nothing is handed down from `main`. A module is a `cpbootstrap.Module` — a name, an `Enabled` flag and a DI sequence — and the sequence is handed a `cpbootstrap.Props` carrying registrars and nothing else:

- `props.RPC.Mount(build, interceptors...)` — the module hands over what *builds* the handler, plus the interceptors it wants. `cpbootstrap` builds it, so it can put its own interceptor outside every module's — see [The error net](error-net.md)
- `props.AdminRPC.Mount(build, interceptors...)` — the same, for an operator service: served on the loopback console listener, and on the admin listener behind `Options.AdminGate` — see [Operator tools](admin.md)
- `props.AdminHTTP.Handle(pattern, handler)` — a plain `http.Handler` on the admin listener alone, **outside the gate's middlewares**: what is served there says who may call it. The connector's OAuth and MCP endpoints are the only ones (see [Claude as a connector](connector.md)). A pattern two modules claim, or one that conflicts with an admin service, refuses the boot; with no admin listener it is not served, and logged
- `props.Admin.Dial()` — the client and base URL of the admin listener, on loopback when it listens on every address: the connector calls the admin services there, as the app the operator let in
- `props.InternalRPC.Mount(build, interceptors...)` — the same again, for what other modules call: served only on the loopback internal listener
- `props.Internal.Dial()` — the HTTP client and base URL a generated `New<Service>Client` takes, to call another module — see [Calling another module](#calling-another-module)
- `props.Sessions` — the click token's check (`cpconnect.SessionVerifier`), one `cpsessionverifier` for the whole process, which a module hands its session interceptors — see [Sessions](sessions.md)
- `props.Runners.Add(runner)` — a `Runner` (`Name()` and `Run(ctx)`), run as a goroutine with the process-lifetime context
- `props.Closers.Add(name, close)` — a cleanup, run in reverse registration order
- `props.Logger`, `props.Metrics`
- `props.Server` — the bind address and the stream heartbeat, **the only config a module reads that is not its own**. It is the transport every module answers over, so it belongs to the layer that owns the server rather than to any context.

**A constructor builds and a `Load…` method reads.** Nothing that reads a file or parses a blob happens inside `New`: the DI sequence calls `New`, then the load, one line each — `embedded_geodesic_map.New` then `LoadGeography`/`LoadBorders`, `inmemory_tile_storage.New` then `Load`, `cpipblock.New` then `Load`, `guard.New` then `Load` (the antibot's evidence), `inmemory_ledger_storage.New` then `Load`.

A module never sees the router, the signal handler or another module's objects. **There is no mutable app object and nothing to leave a half-built dependency on**: `internal/shared/cpbootstrap` builds every module in order, then serves.

**Shutdown goes in this order**: end every open stream, `http.Server.Shutdown` (the public server, then the console, admin and internal ones — a public call in flight may still be waiting on an internal one), the closers in reverse order, then cancel and wait on the runners. A module closes its own Redis client and pool once its runners returned. The first step is the drain interceptor — see [Ending the streams on shutdown](live-streams.md#ending-the-streams-on-shutdown). There are no storage closers left: the tile map, the ledger and the antibot's evidence all flush from their runners, after the closers, once the server has stopped taking writes. The antibot's flushes once its subscribers handled their last facts (`Guard.Hearing`).

**`cmd/api/main.go` is the composition root, and the server's only one** — there is no `internal/app`, because a package whose whole job is to be called once by `main` was a level of indirection and nothing else. It does three things: load the config, build the admin gate (`auth.NewAdminGate`, see [Operator tools](admin.md)), and list the modules. It builds no other object, derives nothing, and reads inside no block.

**The aggregation is the whole of it — a flat slice, no branches, no dependencies threaded through:**

```go
return []bootstrap.Module{
	auth.NewModule(config.Auth),
	planet.NewModule(config.Planet),
	antibot.NewModule(config.AntiBot),
	chat.NewModule(config.Chat),
	player.NewModule(config.Player),
	progression.NewModule(config.Progression),
	scoring.NewModule(config.Scoring),
	gamemaster.NewModule(config.Gamemaster),
	missions.NewModule(config.Missions),
	support.NewModule(config.Support),
	clips.NewModule(config.Clips),
	alerts.NewModule(config.Alerts),
}
```

**Every module is always listed; a module with a switch reads its own.** `NewModule` sets `Enabled` and `cpbootstrap` skips the ones that are off, so turning auth off is a config change and never an edit here. `planet`, `chat`, `player`, `progression`, `scoring` and `support` have no switch and are always on; `auth`, `antibot` and `alerts` have one. A disabled module is never built, so its routes are **absent** rather than present and refusing — `/auth.v1.AuthService/` 404s.

## What two contexts need, without either handing it to the other

`main` builds no objects at all, so a thing two contexts need is **a config block they both declare**, and each builds its own instance from it.

- **`shared/cpsession`** is the click token. The `auth:` block is read by two contexts, but they share no key and no type: `cpsession.SignerConfig` carries the Ed25519 seed and only `auth.Config` declares it, while `planet.Config` declares `cpsession.VerifierConfig`, which is two switches and **no key at all**. `auth` builds a `*Signer`, `planet` a `*Verifier`, **which has no `Mint` on it**. Under the old shared `Config` both built a `*Signer` off one HMAC secret, so `planet` held a live minting object and nothing but discipline stopped it using it.

  **The process asks `auth` for the key** over the internal listener, rather than reading one: `cpbootstrap` builds one `cpsessionverifier` and hands it to every module (`props.Sessions`) — see [Calling another module](#calling-another-module) and [Sessions](sessions.md). So there is one key in the whole file, `auth.secret`, nothing derived for a human to paste, and nothing to keep in step with it.

  Neither module imports the other's packages, and **the planet context knows nothing about Turnstile** — the siteverify client lives at `auth/internal/attestation/turnstile`, so it *cannot* reach it.
- **`shared/cpcountries`** is the ISO list. It is stateless and hardcoded, so each module just calls `cpcountries.New()`, the way it calls `cptime.SystemClock{}`. It sits in `shared` and not under `planet/internal/clicks/` for exactly the reason that layer exists: neither context may depend on the other — and now could not, since that directory is unreachable from chat.

**This is why `auth.secret` is now required** rather than invented at boot — see [Sessions](sessions.md).

## Calling another module

**Over Connect, on a loopback listener, never in the caller's stack trace.** A module that other modules call mounts an internal service with `props.InternalRPC.Mount`; `cpbootstrap` serves it on `httpServer.internalBindAddress` alone, which must be loopback. The caller dials once, in its `module.go`, builds the generated client over `props.Internal.Dial()`, and hands that one client to every adapter that needs it. An adapter takes a narrow port of the procedures it calls (`rpc_account_reader.Auth`, `rpc_player_authors.Player`), never the dialer, so no call builds a client.

**The session key is the platform's, not a module's call.** Checking a click token is the same in every module (the `cpsession` format is the shared kernel), so `cpbootstrap` builds one `shared/cpsessionverifier` and hands it to every module as `props.Sessions`: no module dials auth for the key, and the process asks for it once, not once per module. Until 2026-11-04 nine modules each built their own, and each asked auth once.

- **Each module's data stays in one place.** The caller holds an address, never the other module's config block, pool, objects or root package. The seed is read by `auth` and nothing else.
- **`Dial` is the one place that knows the transport is loopback HTTP.** Moving to unix sockets changes the listener and `internalDialer`, and no module.
- **`Dial` fails with no internal listener**, and a module that calls another refuses the boot. `props.Sessions` is the exception: it dials when it first fetches the key, once per process. An internal service with no listener is not served, and logged, like an admin one.
- **The error net and the drain wrap internal services too.**
- **What travels is a public key**, which is the point: a holder can check a token and cannot mint one, so the hop carries nothing worth stealing. Under the HMAC this replaced there was no such thing to send.
- `TestAModuleCallsAnotherOverTheInternalListener` pins the path, `TestAnInternalServiceIsNotOnThePublicRouter` pins that Caddy cannot reach it.

The proto sits beside the public one in the module's package (`proto/auth/v1/internal.proto`), as `admin.proto` does, and the frontend generates it too without using it.

**The loopback rule is for synchronous calls, and it exists to stop one module loading another's config.** A caller that needs an answer has to reach the module that holds the data. Done in process, that is how `planet` once built a signer off `auth`'s secret and how a key ends up duplicated across blocks in the file. The listener makes the caller hold an address and nothing else.

## Telling other modules what happened

**Over Redis Streams.** An emitter publishes an event and never knows who listens, so it has no reason to load a listener's config, and the problem the loopback rule solves does not arise. Redis keeps what was published until every subscriber has handled it: a restart, a crash or a slow subscriber loses nothing that reached it.

- **The payload is a proto-generated message**, declared in the emitter's proto package (`proto/<name>/v1/events.proto`), and travels as its protobuf bytes. A subscriber imports `generated/proto`, never the emitter's root package, which would also hand it the emitter's `Config`.
- **One stream per type of event** (`events:planet.v1.TilesTaken`), not per emitter: a subscriber hears one type, so it reads only that one, and each stream is trimmed at the pace of its own subscribers. In one stream per emitter, the 40k takes a day would push planet's rare bombs out of the trim window.
- **One consumer group per subscriber**, so each gets every event, in its own copy, in order, in its own runner. No subscriber code runs in the emitter's stack trace: a click waits on one `XADD`, never on a listener.
- **Delivery is at least once and in order per subscriber.** A handler's error is tried again in place after `redis.retryAfter` (2s), doubling up to 64 times that, and the events behind it wait, so the order holds. After `redis.maxDeliveries` (8, about four minutes) the event is buried in `events:dead` with its subscriber and the next one is read. A crash leaves what was read pending; the next boot takes it back first (`XAUTOCLAIM` from `0-0`, whatever consumer held it), before anything new.
- **So a handler sometimes runs twice, and must be safe to.** The bus does not dedupe: no event id, no inbox table. **The domain models the uncertainty**: a fact that may come twice carries the identity of what happened, and the receiver's own state remembers what it applied. See [Idempotent receivers](#idempotent-receivers).
- **A publish Redis does not take is lost, and counted** (`events_unpublished_total{event}`). A fact whose loss would leave two modules disagreeing for good goes through an outbox instead — see [What may not be lost](#what-may-not-be-lost-the-outbox).
- **No two modules are linked both ways.** A module depends on another when its code speaks the other's proto package: it calls it, hears its events or sends it commands; `cmd/api/modules_test.go` refuses a cycle (see [Bounded contexts](bounded-contexts.md)). `chat` asks `player` who posts, so `player` is upstream of `chat`; `chat` publishes `MessageSent`, which `progression` hears, so `chat` is upstream of `progression`. Until 2026-11-04 `player` heard `MessageSent` itself, and the two were linked both ways: that and two cycles like it are why progression left player (see [Progression](progression.md#why-a-module-of-its-own)). The context where a thing happens publishes it in its own language, and the listener translates it at its edge (`message_sent_subscriber`), as it does `TilesTaken`. A downstream module never calls its upstream to report a fact instead.
- **A downstream module that must make its upstream act sends a command in the upstream's language.** The antibot is downstream of planet: it hears planet's facts about callers and decides whom to ban, but the refusal is planet's. Planet defines `RefuseCaller` and `AdmitCaller` in its own package (`proto/planet/v1/commands.proto`), on command streams it handles, and the antibot's adapter (`bans/outbox_planet_enforcer`) translates its bans into them. Planet never names the antibot. See [Asking another module to change something: commands](#asking-another-module-to-change-something-commands).

**Each module builds its own connection, as it builds its own pool.** `cpbootstrap` knows nothing of Redis. The reusable parts live in `shared/cpredis`, and a module's `Config` declares a `redis` block (`cpredis.Config`). Every module's block names the same Redis — `TestEveryModuleOfProductionTalksToTheSameRedis` pins it for the production file. Right after its migrations, a module calls `cpredis.New(config.Redis, props.Metrics)` then `ConnectCtx`, which pings: a module that cannot reach Redis refuses the boot.

- **`Publish(events...)`** is one pipelined `XADD` per call, bounded by `redis.publishTimeout` (500ms), and never fails to its caller: what Redis did not take is counted. **`Send(ctx, events...)`** is the same with an error, for a relay that keeps the events until they are sent.
- **`cpredis.Subscribe[T](ctx, streams, name, handler)`** creates group `name` on the stream of type `T` and answers the `Runner` that reads it and calls `handler.Handle(ctx, event)`. The module adds that runner. A second subscriber of one type with the same name on one connection refuses the boot.
- **`cpredis.SubscribeBatch[T](ctx, streams, name, handler)`** is the same for a `BatchHandler`, whose `HandleBatch(ctx, events)` takes what one read gave (100 events at most, in the stream's order) and is acked with one `XACK`: a subscriber that writes per account or per round groups the batch and writes each group once. **A batch that fails is handled again one event at a time**, each tried again in place and buried alone as below, so the order holds and one poison event never holds the rest; a handler must be safe to run again on any slice of a batch, which the marks of [Idempotent receivers](#idempotent-receivers) give. Planet's takes and shields struck are heard this way (2026-11-07).
- **A group is made from the start of the stream**, and an existing one is kept: what another module published before this one subscribed is read too, so the order of modules in `cmd/api` does not matter. A publish always adds to the stream, since no module knows every subscriber. **So a group keeps its name when its module is renamed**: a new name is a new group, which reads the stream again from its start. The scoring module's groups on `TilesTaken` are still `seasons-standings` and `seasons-rounds`, and the groups progression took from player are still `player-stats…`, `player-titles` and `player-finale-fights`.
- **The start of a stream is what the trim left of it**, not every event ever told: an event every group of the stream handled is gone within a minute (below). So a subscriber that moves from one event to another loses what its old group had not handled and its new stream no longer holds, unless the emitter tells it again. When the modules moved from `auth.v1.AccountDeleted` to `player.v1.PlayerForgotten` on 2026-11-04, player read auth's stream again under a new group to tell each deletion again: see [Player](player.md#the-deploy-that-moved-the-others-to-players-events).
- **A group nobody subscribes with any more stays**, and holds its stream's trim back to `redis.maxLen`. A renamed or removed subscriber needs `XGROUP DESTROY events:<type> <old name>` by hand once the release is out, and a stream nobody publishes to any more a `DEL`. The split of progression from player left three groups and a stream: see [The deploy that split it](progression.md#the-deploy-that-split-it). The move to player's events left thirteen groups on auth's streams: see [Player](player.md#the-deploy-that-moved-the-others-to-players-events). The move to one fact per act (2026-11-07) left `events:planet.v1.TileTaken` and `events:planet.v1.ShieldStruck` with their groups: a `DEL` of each once the release is out.
- **Memory is bounded twice.** Every minute each subscription cuts its stream (`XTRIM MINID ~`) to the oldest entry one of the stream's groups has not handled, so a stream holds only what is still in hand while every subscriber keeps up. And each `XADD` caps its stream at `redis.maxLen` (100k entries), for a stream whose subscriber stopped. **That cap drops entries no group read**, whatever the groups (Redis 7.4 has no `ACKED` trim), which is why a fact is one entry per act and not one per tile: when planet told one `TileTaken` per tile, an enclose of a continent alone was more than 100k entries (see [Enclose](enclose.md#giant-pockets-measured-2026-11-07)). Redis runs with 64 MB and `noeviction`: a full Redis refuses events, counted as unpublished, rather than drop unread ones.
- **Metrics**: `events_failed_total{event, subscriber}` what a handler refused, `events_dead_total{event, subscriber}` what was buried, `events_lag{event, subscriber}` what is in the stream unread, `events_pending{event, subscriber}` what was read and not acked (read from `XINFO GROUPS` at each scrape), and `events_unpublished_total{event}`, one counter every module's connection shares. The bus logs nothing: a subscriber that wants a log line wraps its handler in a decorator (`player`'s `log_subscriber`).
- **At shutdown** a runner finishes and acks what it read, reads what is left without waiting (ten batches at most), and stops; what it does not reach waits in Redis for the next boot. A handler runs on a context the shutdown does not cancel. A store a handler writes to must outlive it: `cpredis.CloseAfter(streams, logger, runners...)` closes the client once the module's subscribers returned, inside `cppg.CloseAfter`, which closes the pool after that.
- **Tests:** `redis_test.go` runs against a real Redis (`cpredis.StartTestServer`, behind the tag, a `redis:7.4-alpine` container per test), each module on its own connection: every module reads every event in order though it subscribed after the publish, a copy each, no subscriber code in the publisher's stack trace, a duplicate name refused, no Redis refuses the connection, a failure tried again before the events behind it, a poison event buried where `XRANGE events:dead` shows it, what a crash left pending handled first at the next boot, the shutdown, a batch subscriber handed what one read gave at once, and a failed batch handled again one event at a time with its poison event buried alone. `subscription_internal_test.go` pins the trim. `cpredis.RecordedEvents` (behind the tag) stands in for the bus where a use case only publishes.

### Idempotent receivers

| subscriber | why a second delivery changes nothing |
|---|---|
| `player-stats`, `player-stats-bombs`, `player-stats-fortifies` (progression's) | `planet` tells its map facts in ledger order with their `position`, and each take with its `index` in its event. The stats row keeps a mark past the last take, bomb and fortify it counted (`stats.Counted`); one below it was counted already. A take's mark is its position and index (`stats.TakeMark`): a spread or an enclose is one ledger event, at one position, that holds several takes, and a batch's takes of one account are folded in order in one write |
| `player-stats-messages`, `player-stats-bonuses`, `player-stats-quizzes` | the same with the time of the last message, box and right answer counted, compared to the microsecond postgres keeps |
| `player-stats-missions` | `missions.v1.MissionsPaid` says how many missions the account was paid in all; the stats keep the highest number heard |
| `seasons-standings` | the tally keeps the position and index past the last take it counted (`standings.Tally.TakesBelow`: two columns of each contributions row, the highest pair is the tally's), written with each account's takes of a batch in one transaction per book; a batch told again, or one event at a time after it failed, finds its takes under the mark |
| `seasons-rounds` | each round keeps the position and index past the last take it counted (`rounds.counted_takes_below`, `counted_takes_below_index`), locked and moved in the one transaction that counts a batch's takes past it (`books.TakeMark.Uncounted`) |
| `missions-progress` | an account's day keeps the position and index past the last take it counted (`missions.Counted.TakesBelow`, `mission_sheets.counted_takes_below`, `counted_takes_below_index`), moved in the one transaction that counts the account's takes of a batch for that day; the index goes on across an event's parts, so a batch told again, whole or one event at a time after a failure, counts nothing twice |

### What may not be lost: the outbox

A fact goes through an outbox when its loss would leave the modules disagreeing for good, with nothing to tell it again:

- `auth.v1.AccountDeleted`: a lost one keeps a deleted player's personal data in player, and in every module player tells `PlayerForgotten`. `purge_deletions_usecase`, `delete_account_usecase` (a guest's) and `prune_guests_usecase` record it in the transaction that deletes the account.
- `auth.v1.AccountDeletionRequested` and `AccountRestored`: a lost one leaves an account the player asked to delete shown to everybody, or one that came back hidden, for good. `delete_account_usecase` records the first in the transaction that marks the account, and `signin.Admitter` the second in the transaction that clears the mark.
- `auth.v1.SignedIn`: a lost one leaves a linked account with no username, shown as a guest, until its next sign-in, and the missions it finished as a guest that day unpaid. `signin.Admitter` records it in the transaction that saves the sign-in.
- `auth.v1.DiscordJoinGranted`: a lost one is a Discord sign-in that never joins the game's server, though the player
  gave leave to. `signin.Admitter` records it in the transaction that saves the sign-in and keeps the grant it names.
  It holds no token: the alerts module asks auth for it by the grant's id (`GetDiscordGrant`).
- `planet.v1.RefuseCaller` and `AdmitCaller`, from the antibot: a lost one leaves a ban the antibot keeps and planet never refuses, or a lifted one planet keeps refusing. `bans.Banner` records the command in the transaction that changes the ban row, under the ban's lock. At each rule set it takes, the first at boot, the antibot records one again for every running ban (`bans.Book.Restate`), so the bans running at a deploy reach planet's new table too, and a set that stops enforcing admits them.
- `scoring.v1.RoundMissed` and `BookMissed`: a close of a round or book scoring never opened. A lost one is told again
  at the gamemaster's next close, a minute later, so the outbox is not needed for loss; it is there so the answer is
  recorded in the order of scoring's other answers. `close_round_usecase` and `close_book_usecase` record each in a
  transaction of its own.
- `scoring.v1.RoundScored` and `BookClosed`: the round is scored once and the book closed once, so a lost one is never sent again and the gamemaster never tells that day, battle or season ended. Scoring records each in the transaction that scores the round or closes the book, only when this call did it.
- `planet.v1.ArenaOpened`: a lost one is an arena battle whose round never opens, so it scores nothing, since an arena
  opens once. Planet records it in the transaction that keeps the arena open, before its map plays (`Storage.Blank`).
- `planet.v1.ArenaClosed`: a lost one is a day after an arena battle that never opens, since an arena closes once. Planet
  records it in the transaction that closes the arena and deletes its map (planet's first outbox, `planet-outbox`).
- `gamemaster.v1.DayEnded`, `BattleEnded` and `SeasonEnded`: the gamemaster records each in the transaction that keeps what it heard from scoring, only when it is new, so the chat announces each podium and champion once.
- `gamemaster.v1.DayStarted`: the gamemaster records it in the transaction that keeps the day told (`told_days`), only when the day is new or its end moved, so missions keeps each day once.
- `gamemaster.v1.SeasonStarted` and `BattleStarted`: the gamemaster records each in the same transaction, keeping the season and the battle told (`told_seasons`, `told_battles`), only when new, so the alerts ping each start once.
- `player.v1.PlayerCreated`: a lost one is a new player that never gets its refill, nor a nameplate in progression, nor a rank on scoring's boards, since the profile is made once. `name_account_usecase` and `set_name_usecase` record it in the transaction that makes the profile.
- `player.v1.PlayerNamed`: a lost one leaves a Discord member under its old nickname until its next rename or the
  operator's `LinkMembers`. `name_account_usecase`, `set_name_usecase` and `rename_player_usecase` record it in the
  transaction that saves the name.
- `player.v1.PlayerSignedIn`: a lost one is the missions a guest finished that day never paid, since that sign-in is told once. `tell_sign_in_usecase` records it on every `auth.v1.SignedIn`, in a transaction of its own.
- `player.v1.PlayerLeaving` and `PlayerReturned`: a lost one leaves progression showing the badges of an account player hides, or hiding one player shows again, and scoring ranking it or not, for good. `decide_departure_usecase` records one for every decision, in the transaction of the departure.
- `player.v1.PlayerForgotten`: a lost one keeps a deleted player's data for good in every module that hears it: its stats and titles in progression, its name on its takes in planet, its tallies in scoring, and the rest. `forget_account_usecase` records it in the transaction that deletes the profile and the guest code, for every account auth deleted.
- `planet.v1.GrantCharges`, a command: a lost one is a mission paid that planet never granted. `missions`' `payroll` records it with the payment.
- `missions.v1.FlagMissionDone`: a flag's mission is done once, so a lost one is a line the chat never shows. The flag
  mission's use cases record it beside the `scoring.v1.GrantPoints` of its points, in the transaction that finishes it.
- `support.v1.PlayerReported`: a lost one is a report the chat's judge never reads, left to the operator's eyes alone.
  `report_player_usecase` records it in the transaction that keeps the report.
- `support.v1.DecideReport`, a command, and the `chat.v1.AccountMuted` of a mute the judge gave: a lost decision leaves a
  report open that the chat acted on, and a lost announcement a mute nobody saw. `judge_report_usecase` records both in
  the transaction that removes, mutes and keeps the judgement; the relay sends the command to support's stream and the
  event to the listeners (`redis_outbox_sender`), from one outbox.
- `missions.v1.MissionsPaid`: it is told with the payment it counts, so it shares the grant's transaction. The relay sends the grants as commands and it as an event (`redis_outbox_sender`), from one outbox.
- **Not the gamemaster's commands** (`PlayRuleSet`, `ResetMap`, `ScoringCommand`, `ArenaCommand`): the clock decides them, not a transaction. The
  gamemaster's runners send them with `streams.Commands().Send` and keep what they told only once Redis took it, so a
  refused send is sent again the next second, and each boot sends again what holds (see [The gamemaster](gamemaster.md)).
- `planet.v1.TilesTaken`, `BombLanded`, `Fortified`, `FlagKnockedOut`, `ShieldPlaced` and `ShieldsStruck`: **the ledger is their outbox.** `ledger/usecases/relay_ledger_usecase` reads what the ledger flushed past `planet.ledger_relayed`, sends it, then moves the row. A take a hard kill loses before its flush is never told, so the stats and the standings never count what the ledger does not hold; a crash between the send and the move tells the batch again, which the marks make harmless. The migration put the row after the last take the old server had published. When the takes and the shields struck moved to one fact per ledger event (2026-11-07, `20261107200000_relay_takes_per_event`), a migration moved the row back to the first event of the last hour, so the new streams tell again what the old ones held unread, and the marks skip what was counted.

Not in an outbox, because a loss is harmless or the next event repairs it: `SignedOut` (the roster drops the visit when it expires), `MessageSent`, `BonusClaimed` and `QuizAnswered` (a stat short by one), an operator's `AccountMuted` (an announcement missed), `progression.v1.StatsChanged` (the next one grants the title), `planet.v1.AllegiancePledged` (a role or a room stream that follows the flag at the next pledge), and planet's facts about callers (`ClickTried` and the rest: a try or a read short, in a watchdog's window). Those go through `facts.Relay`, which sends what `facts.Log` holds every 100ms with `Publish`, in order: a crash loses the last 100ms of them.

**`shared/cpoutbox`** is the mechanism. **Recording an event is the use case's decision**: it opens a transaction and calls `Outbox.Record(ctx, events...)` beside its stores — see [Transactions](transactions.md). `cpoutbox.New(db).Record` inserts each event in the module's `outbox` table (`position bigserial`, `event outbox_event`, `payload bytea`) in the transaction `ctx` carries, and refuses outside one. `outbox_event` is an enum of the events that module keeps there, so a new one is a migration. `cpoutbox.NewRelay(name, db, streams, logger)` is a runner that, every second and once more at shutdown, locks the oldest rows (`FOR UPDATE SKIP LOCKED`, 100 at a time), `Send`s them in order and deletes them in the same transaction: Redis down keeps the rows for the next tick. A row that does not decode is dropped and logged rather than left to hold every row behind it. `cpoutbox/outbox_test.go` pins it; each use case's test pins what it records, with `cpatomic.FakeOutbox`.

### Asking another module to change something: commands

**A command, over Redis Streams, through the sender's outbox.** A module that needs another to change its own state
does not call it: it records a command in the receiver's language (`proto/<receiver>/v1/commands.proto`,
`planet.v1.GrantCharges`) in its outbox, in the transaction of what decided it, and the relay sends it. The receiver
never learns who sent it, as an emitter never learns who listens. The rule schedule's commands, which the clock
decides, are sent straight (see [The rule schedule](gamemaster.md)).

- **One stream per type of command** (`commands:planet.v1.GrantCharges`), apart from the events, with **one group**
  (`handler`): the module that owns the command reads each one once, in order, and one sent before it listened too.
  `cpredis.Handle[T](ctx, streams, handler)` is that runner; a second `Handle` of one command on one connection refuses
  the boot. `streams.Commands()` is what an outbox relay sends with: `cpoutbox.NewRelay(name, db, streams.Commands(),
  logger)`.
- **Delivery is the events' own**: at least once, a failure tried again, a poison command buried in `events:dead`. So
  **a command names itself** (`grant_id`), and the receiver keeps what it applied in the transaction of the change.
- **No answer comes back.** The sender decides with what it knows; what the receiver refuses or caps is its own rule: a
  grant past the stack is not granted.
- **A read stays an RPC** (see [Calling another module](#calling-another-module)): a command is for a change.
- `redis_test.go` pins a command sent before its handler listened, a command that is no event, and one handler.

Adding a context that callers talk to means a `proto/<name>/v1`, an `internal/<name>/` with a `module.go`, one line in the slice, and a `handle` for its public service in `deploy/vps/caddy/Caddyfile`. Connect derives the route from the proto package, so there is no prefix to allocate and no router to edit; but Caddy answers 404 for a path it does not list, and the client reads that 404 as a service the server does not offer. `TestCaddyRoutesEveryPublicService` fails for a public service Caddy does not route.

**`cmd/api`** is the server, and the only binary the image holds: `main.go` is the composition root, about 85 lines of config and a module list, and `cpbootstrap` is the rest. **`cmd/clips`** is the other binary, a job a workflow runs with `go run` — see [The clips job](clips-job.md).

It runs as **one container beside a postgres and a Redis**: the tile map lives in process, and postgres is where it is kept between boots — see [Durability](durability.md); Redis carries the events between modules and nothing else — see [Telling other modules what happened](#telling-other-modules-what-happened). There is no cache and no second API process.
