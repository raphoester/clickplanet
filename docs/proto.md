# Shared protobuf contract

`proto/` is the **single source of truth** for the API contract — every app generates its own bindings from it (nothing here is hand-copied between apps). One package per bounded context:

- `proto/planet/v1/planet.proto` — the tile game (`ClickService`)
- `proto/chat/v1/chat.proto` — the live chat (`ChatService`)
- `proto/auth/v1/auth.proto` — who a caller is (`AuthService`): the mint that gates `Click`, the identity token resumed from the cookie, the caller's account, sign-in with Google, Discord or an emailed code, sign-out and deletion
- `proto/session/v1/session.proto` — the deprecated mint (`SessionService`), served by the same auth module until no client calls it
- `proto/player/v1/player.proto` — a player's name, color, stats, titles and the countries it plays for and against, and who is playing (`PlayerService`); the colors themselves are `NameColor` in `color.proto`, and a title is `Title` in `title.proto`, which `chat.proto` and `scoring.proto` import too
- `proto/scoring/v1/scoring.proto` — a points accountant's books and rounds, read by the ids the gamemaster's timeline names: a book's board and scores, a round's live standings or results, the caller's tally (`ScoringService`). No season, day or battle: those are the gamemaster's words
- `proto/missions/v1/missions.proto` — the caller's three to five missions of the day, how far it took them, and which are paid (`MissionService`); each kind of mission is its own message in a `oneof`, so a new kind adds a message and no field
- `proto/support/v1/support.proto` — what a player sends the operator: a feature suggestion or a bug report, with photos or videos, or a report of another player (`SupportService`)
- `proto/gamemaster/v1/gamemaster.proto` — what the schedule plays now, in the players' words: the `Turn`, the kind of the running entry (`EntryKind`: plain, or battle), the operator's description of its rules, since when and until when, and the entry's id that scoring's round of its own repeats, never a rule set's name, and the `Timeline`, the battles to come (`GamemasterService`: `ListenForEvents`, the turn and the timeline then each change of either, and `GetTurn`, the same as a cached GET); the timeline carries the season that runs and the next one, today's day, and each battle's times, all with the ids of their books and rounds in scoring, and the stream tells each `Debrief`: a day, a battle or a season scoring scored. Beside it, `events.proto` is what the gamemaster tells the other modules in the game's words (`DayEnded`, `BattleEnded`, `SeasonEnded`). Beside it, `admin.proto` is the rule schedule: which rule set planet, the antibot and scoring play, of which kind, with which words for the players, and when (`gamemaster.v1.AdminService`: `GetSchedule`, `AddEntry`, `EditEntry`, `DeleteEntry`), and the seasons, each with its optional finale, the Final Battle (`GetSeasons`, `AddSeason`, `EditSeason`, `DeleteSeason`; `GetSchedule` lists the finales beside the entries)
- `proto/antibot/v1/admin.proto` — the operator's bans and rules (`antibot.v1.AdminService`: `BanPlayer`, `UnbanPlayer`, `InspectPlayer`, `GetRules`, `SaveRuleSet`). No public service: the antibot hears planet and answers only the operator. Beside it, `rules.proto` is `antibot.v1.Rules`, every bound of a rule set, which postgres also keeps as protojson
- `proto/clips/v1/clips.proto` — what the frontend's clip generator hands the backend's job that posts its clips: the findings its model editor makes the stories from (every front, tour and place measured, with their top fighters, and the season's stories), the story the job hands back to render (`Pick`), what to post with each clip, and a run's `Cast` (numbers and names, never an account). No service: all are written as JSON files in one workflow run. Beside it, `admin.proto` is the numbers of the clips the job posted, a snapshot a day, and the players each names (`clips.v1.AdminService`: `KeepSnapshot`, `ListSnapshots`, `ListRows`, `MakeCast`, `KeepAppearance`): the job keeps them over ssh, the backoffice reads the numbers. `appearances.proto` is the public `ClipsService`: the posts that name the caller

Beside them, `internal.proto` is what one backend module asks another, or `auth`'s admin gate asks `auth` (`auth.v1`, `player.v1`, `planet.v1`, `antibot.v1`, `scoring.v1`), `events.proto` is what one tells the others over Redis Streams (`planet.v1.TileTaken`, `auth.v1.AccountDeleted`, `scoring.v1.RoundScored`, `gamemaster.v1.SeasonEnded`), and `commands.proto` is what one asks another to change, in the receiver's words (`planet.v1.GrantCharges`, which missions sends, `planet.v1.RefuseCaller`, which the antibot sends, `planet.v1.PlayRuleSet`, `planet.v1.ResetMap`, `antibot.v1.PlayRuleSet` and `scoring.v1.ScoringCommand`, which the gamemaster module sends). None is on the public router; the frontend generates them without using them. `planet.v1`'s `ledger.proto` is the ledger's read, served on its `AdminService` and its `InternalService` alike. `admin.proto` is what an operator calls (`AdminService`, in `antibot.v1`, `auth.v1`, `chat.v1`, `clips.v1`, `planet.v1`, `player.v1`, `gamemaster.v1` and `support.v1`): over SSH on the console listener, and from the admin page on the admin listener, which only a signed-in operator passes.

Connect derives each service's route from its proto package, so a new context gets its own path with no prefix to allocate. Every `buf.gen.yaml` input points at the whole `proto` directory, so a new package is picked up by each generator with no config change.

After editing a `.proto`:

```bash
cd apps/backend && make proto   # regenerates apps/backend/generated/proto
cd apps/frontend && npm run proto   # regenerates apps/frontend/src/gen/grpc
cd apps/backoffice && npm run proto   # regenerates apps/backoffice/src/gen/grpc
```

Every app's `buf.gen.yaml` reference `../../proto` (or `../../../proto` for the backend, whose config lives one level deeper at `apps/backend/proto/`) — do not create per-app copies of the `.proto` files again.
