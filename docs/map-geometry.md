# Shared map geometry

`map/` is the **second thing the apps share**: the **boards**, each a geometry as a set of files of its own, in
`map/boards/<name>/`. There are three: `earth-1`, which the world played until its switch, and all history before;
`earth-2` (1,004,682 tiles, 13 km apart), which it plays after, and `siege-1` (27,259, 79 km), Capital Siege's, both
warped and rotated so every cell covers about as much ground and the twelve five-neighbour points are at sea. Beside
them, `map/carries/` holds the carry-over from `earth-1` to `earth-2`, each new tile's parent, which the switch reads
(the backend's copy alone). A board's manifest says which lattice it is cut from, how many
tiles it has and the hash of their positions; its runs say which lattice points are tiles, and so where every tile
is and what a tile id means; its borders say which country's ground each tile sits on; its capitals and bridges are
what an arena battle's rules read; its terrain is what the globe draws at each point of the lattice. **They are written by one command from one oracle**, so "is this sea or land" and
"which country is this" cannot disagree and a tile in no country cannot be built. See
[`map/README.md`](../map/README.md), and [Boards](boards.md) for the design and what comes next.

**There is no coordinates file.** Every app rebuilds the positions from the lattice and the runs, to the bit: the
page in a worker, the backoffice with its own copy of the lattice module, the backend in Go, the scripts with the
page's module. Each checks its rebuild against the manifest's `positionsHash`.

It follows the `proto/` precedent rather than inventing a second pattern. The root holds the source;
each app carries a **committed, byte-identical copy** generated by a target, because each app's
Docker build context is its own directory and none can read the repo root at build time:

```bash
cd apps/frontend && npm run map:generate -- earth-2   # rewrite a board in /map from Natural Earth (earth-1 with none named)
cd apps/backend && make map    # → apps/backend/generated/map/boards (embedded)
cd apps/frontend && npm run map   # → apps/frontend/static/boards (fetched at runtime) and boardsAsset.ts
cd apps/backoffice && npm run map   # → apps/backoffice/src/gen/map (the manifest and the runs, bundled)
```

**A cell that is mostly lake is water**, from Natural Earth's lakes, so the Great Lakes, Victoria and Baikal are not
tiles; a usually dry one, such as Lake Eyre, stays land. **Every country has a tile.** One the lattice misses — the
Vatican, Monaco, the Maldives, Palau — gets one point, its seat: a neighbour's on a continent, the sea's over its main
island otherwise. The lists are `apps/frontend/scripts/map/seats.mjs`, one a board (34 on `earth-1`, 15 on `earth-2`,
52 on `siege-1`), and `npm run map:audit -- <board>` fails on a flag with no ground.

Each file is content-addressed, so all copies carry the same name or one of them is stale.
The backend rebuilds a board's tiles and their adjacency from its copy the first time it plays it, and **refuses the
board** (and so the boot, for the board the map plays) if the positions do not hash to the manifest's or a file holds
another tile count than the manifest — drift here silently moves every player's territory, so it is worth a crash.
Every board an app carries needs a row in planet's `boards` under the same hash, or the boot refuses.

**Regenerating renumbers every tile**, since a board's ids are ranks among its tiles (in three's walk on `earth-1`, in
canonical id order on the others). Positions
do not move, so `npm run map:generate -- --remap <path.up.sql>` writes the postgres migration that
follows every owned tile across; `map/README.md` has the checklist.
